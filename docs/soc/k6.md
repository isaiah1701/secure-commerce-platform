# Bounded SOC traffic

Traffic is accepted only for <https://shop.platf0rm.site>. Use dedicated synthetic
`soc-*@platf0rm.site` identities; password spray requires five distinct
`soc-spray-*` accounts. No script creates GLPI tickets or Sentinel incidents.

## Repeatable execution

From the repository root, with Azure CLI authenticated and k6 installed:

```bash
PYTHONPATH=. backend/.venv/bin/python soc/validate.py run auth-lockout
PYTHONPATH=. backend/.venv/bin/python soc/validate.py verify <printed-scenario-id> --wait 900
```

The helper warms readiness, provisions fresh synthetic customers through the normal
registration API, invokes k6, and saves sanitized evidence under `docs/soc/evidence`.
Credentials are random and remain in protected runner files outside Git; they are
not printed or passed as command-line arguments. Integration credentials stay in
Key Vault. A verification timeout is not success: inspect and repair the failed stage,
then verify again without manufacturing an incident or case.

Supported executions:
- `auth-lockout`: eight invalid login attempts, one account, two-second spacing.
  The first five fail normally; account lockout is enforced. No valid login is sent.
- `password-spray`: one invalid attempt per five synthetic accounts, two-second spacing.
- `auth-success-after-failures`: three failures then one genuine known-credential
  success for the **same** account, below the five-failure lock threshold. This
  produces a suspicious sign-in signal, not evidence that compromise occurred.
- `registration-abuse`: five rejected duplicate registrations; not unauthorized creation.
- `privilege-probe`: customer login and three read-only admin endpoint denials;
  not successful privilege escalation.
- `admin-directory`: real synthetic administrator login and three directory reads.
  Use the existing secret without printing it:

```bash
PYTHONPATH=. backend/.venv/bin/python soc/validate.py run admin-directory \
  --user soc-admin-training@platf0rm.site --password-secret soc-lab-admin-password
```

Keep at least 65 seconds between independent authentication runs to avoid sharing
the ten-per-minute control window. All scenarios use one VU and at most one request
per second. Warmup performs at most two readiness requests before scenario traffic;
a failed warmup stops the run. `KILL_SWITCH=true` disables k6 traffic. Expected
authentication errors are explicit expected HTTP statuses, but every scenario
check must pass and network failures must be zero.

Additional bounded capabilities in `scenarios.js` include `suspicious-api`,
`auth-rate-limit` and `multi-event`. Their checks are not automatically evidence
of a complete Sentinel chain. The separate `api-read-burst.js` caps traffic at
60 read-only API requests over at least 60 seconds. Registration/account-control
limits are not disabled for tests.

## Validation

```bash
(cd backend && PYTHONPATH=. .venv/bin/pytest -q)
backend/.venv/bin/ruff check backend soc/validate.py
node --test soc/k6/*.test.mjs
terraform -chdir=infra fmt -check -recursive
terraform -chdir=infra validate
```

Use a scenario as the investigation pivot:

```kusto
ContainerAppConsoleLogs_CL
| where TimeGenerated > ago(1h)
| where ContainerAppName_s == "secure-commerce-dev-app"
| extend payload=parse_json(Log_s)
| where tostring(payload.simulation_id) == "<scenario-id>"
| project ActivityTime=todatetime(payload.timestamp), payload
| order by ActivityTime asc
```

Use [the progress table](scenario-progress.md) for the exact scope and full-chain
evidence. Neither unit tests nor an HTTP 200 establish a Sentinel incident or ticket.
